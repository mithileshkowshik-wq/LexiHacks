# Worksheet Sections — Handoff (2026-08-12)

## What this is

`server/data/worksheetSections.live.json` — the catalogue that drives which 2-3 page
worksheet section gets recommended per error category in **live** (non-mock)
recommendation mode — went from **5 hand-typed placeholder entries** (all uniformly
claiming "pages 1-3", never individually verified) to **70 real, content-grounded
entries** covering all 5 error categories, generated by actually reading every
approved worksheet PDF and asking Gemini to propose sections.

## Why it needed fixing

Two things were broken before today:

1. Live mode wasn't even reading this file — `WORKSHEET_SECTIONS_PATH` was never set,
   so it silently fell back to the mock-only default and failed closed with
   *"No approved worksheet sections are configured for this recommendation mode."*
   Fixed (see git history, `docs: correct stale port-4000 references...` and related
   commits from earlier the same day).
2. Once that was fixed, every one of the 5 entries turned out to claim "pages 1-3" —
   verified against the real PDFs, two of the five referenced worksheets were
   **genuinely 1-page documents**, which can't validly have any 2-3 page section at
   all (the code requires spans of exactly 2 or 3 pages). This was placeholder data,
   never checked against reality.

## What was built

`server/scripts/generateWorksheetSectionCandidates.mjs` — a reusable batch job, not a
one-off script:

- Fetches the full approved worksheet catalogue directly from Azure (185 PDF entries;
  32 are exact-duplicate files reused across "Band A"/"Band B" folders, collapsing to
  **153 unique worksheets**).
- Extracts real per-page text from every PDF (`pdfjs-dist`).
- Asks Gemini, per document, to propose 2-3 page candidate sections for any of the 5
  error categories (`phonological`, `orthographic`, `morphological`, `capitalisation`,
  `punctuation`) — only where the content genuinely supports it. Empty result is a
  valid, expected outcome for documents that don't fit any category.
- Checkpoints after every document (`.worksheetSectionCandidates.checkpoint.json`) so
  a run can be killed and resumed (`RESUME=true`) without redoing completed work.
- Retries transient failures (429 rate-limit with the API's own suggested delay, 503
  "high demand") with backoff; after several consecutive rate-limit failures in a row,
  stops the run rather than burning through the rest of the catalogue against an
  exhausted key.
- Writes `server/data/worksheetSections.candidates.json` — explicitly labelled
  unreviewed, separate from the live file.

## What was run

153 unique worksheets processed to completion. Along the way: the first Gemini API
key hit a **hard daily free-tier quota wall** (`generate_content_free_tier_requests`)
after ~100 requests and never recovered even with backoff; several more free-tier keys
were cycled through, each contributing a batch before also hitting a wall, until the
full catalogue was covered. **70 candidate sections found:**

| Category | Count |
|---|---|
| phonological | 32 |
| morphological | 19 |
| punctuation | 9 |
| orthographic | 6 |
| capitalisation | 4 (1 also tagged `unsure`, preserving the original file's fallback coverage for uncertain-category errors) |

2 permanent failures, left out entirely: one password-protected PDF (`pdfjs-dist`
can't open it without a password), one document that exhausted its 503 retries.

39 of the 153 documents contributed at least one section; the rest genuinely didn't
fit any category and were correctly left empty rather than force-fitted.

## What changed live

**Human review of the 70 candidates was explicitly skipped on this pass, by
instruction** — normally the recommendation here would be to spot-check a sample
per category before promoting anything (see `server/README.md`'s "use an ignored,
*reviewed* JSON file" note; live worksheet recommendations feed a clinical tool). That
step did not happen this time. If anything looks wrong in a real recommendation,
`worksheetSections.candidates.json` has every candidate's Gemini-written rationale for
tracing back why it was proposed.

All 70 were converted into the live file's exact schema and validated against the
app's own `validateWorksheetSections()` logic before being written — this passed
cleanly (worksheetId exists in the 185-entry approved catalogue, page range is exactly
2-3 pages, categories are valid, no duplicate worksheetId+page-range pairs).
`server/data/worksheetSections.live.json` now has all 70 entries.

## Re-running / extending later

```bash
cd server
GEMINI_API_KEY=<a key with quota> RESUME=true node scripts/generateWorksheetSectionCandidates.mjs
```

`RESUME=true` skips anything already checkpointed. To redo the 2 permanent failures,
remove their `worksheetId` from the `done` map in the checkpoint file first (same
pattern used mid-run today to un-stick wrongly-marked rate-limit failures).
