================================================================================
LEXIPATH API - ROUTE REFERENCE
Scope: Error Classification Engine and Recommendation Engine prototype routes.
Base path: /api
================================================================================

CONVENTIONS
-----------
- All request and response bodies are JSON, except sample upload (multipart)
  and image serving (binary).
- IDs are generated by the server. Clients never send an id when creating.
- Error responses use a single shape:
      { "error": { "code": "SAMPLE_NOT_FOUND", "message": "..." } }
- Status codes used: 200 OK, 201 Created, 202 Accepted, 400 Bad Request,
  404 Not Found, 422 Unprocessable Entity, 500 Internal Server Error.
- Every route below except /api/auth/* requires a signed-in caller (a JWT
  from POST /api/auth/login, sent as `Authorization: Bearer <token>`) - a
  request with no token or an invalid one gets a 401. What's still missing is
  authorization: nothing scopes a request to the caller's own students, so
  the per-route notes below about teacherId and "returns every student" are
  still accurate. That gap is a deliberate cut, not an oversight - see NOTES
  AND DEFERRED at the bottom.


================================================================================
STUDENTS
================================================================================

POST /api/students
------------------
Creates a new student record.

Body:     { "name": String, "currentGrade": String, "teacherId": String? }
Returns:  201 + the created Student, including the server-generated studentId.
Errors:   400 if name or currentGrade is missing.

Notes:
  - studentId is minted by Mongo. Do not accept one from the client.
  - teacherId is optional while there is no auth. Once login exists it comes
    from the session instead of the body.


GET /api/students
-----------------
Lists all students.

Returns:  200 + array of Student objects.

Notes:
  - With no auth this returns every student in the database. Acceptable for
    the prototype; would be scoped to the logged-in Teacher in production
    (Teacher "may teach" Student, 0..*).


GET /api/students/:studentId
----------------------------
Fetches one student's core details.

Returns:  200 + Student { studentId, name, currentGrade }
Errors:   404 if no student with that id.

Notes:
  - Does not embed samples or reports. Use the routes below for those - keeps
    the payload predictable and avoids an expensive join on every profile load.


GET /api/students/:studentId/samples
------------------------------------
Lists the samples belonging to one student. Backs the UI's select(sample).

Query:    ?status=PENDING|PROCESSING|COMPLETE|FAILED   (optional filter)
Returns:  200 + array of Sample summaries:
              { sampleId, uploadedAt, analysisStatus, imageCount }
Errors:   404 if the student does not exist.

Notes:
  - Deliberately a summary, not the full Sample. Do not return sampleImages or
    sampleContent here; the list screen does not need them and the payload
    grows fast.
  - Sort newest first. The therapist almost always wants the latest upload.


================================================================================
SAMPLES
================================================================================

POST /api/samples/:studentId
-----------------------------
Uploads a new handwriting sample and starts analysis.

Content-Type: multipart/form-data
Path:     studentId  (String) - which student this sample belongs to.
Fields:   samples    (one or more image/PDF files - the field name is
                      "samples", not "images"; a multi-page PDF is split
                      into one page per file server-side)
          title      (String) - falls back to the first file's name if blank
          taskType   (String) - ESSAY | LONG_ANSWER | SHORT_ANSWER
Returns:  202 + the created Sample, with analysisStatus = UPLOADED and the
          server-generated sampleId.
Errors:   400 if no file was attached, or if :studentId doesn't resolve to a
          real student.
          422 if the real content-sniffed file type isn't JPG/PNG/PDF, a PDF
          can't be rendered, or a file exceeds the size ceiling.

Maps to:  sampleController.createSample(req, res) (server/controllers/sampleController.js)

Notes:
  - studentId is a route parameter (not a body field), and the file field is
    named "samples" - settled differently than the shape first sketched here,
    kept as the source of truth for whichever came later. See
    client/src/lib/api.js's uploadSample() for the exact request shape.
  - The client does NOT send a sampleId. It reads it off the response and uses
    it to poll.
  - 202, not 201: the Gemini vision call takes seconds, so the request returns
    as soon as the Sample row exists and analysis continues in the background.
    ErrorClassificationEngine.analyse() runs after the response is sent. This
    was the "decision point" flagged in an earlier draft of this doc - 202 is
    what's implemented.


GET /api/samples/:sampleId
--------------------------
Fetches one sample. This is both the polling target after upload AND the
full payload behind the scan-beside-errors review screen - see the note
below on why there is no separate /report endpoint.

Returns:  200 + Sample { sampleId, title, studentId, taskType, uploadedAt,
                         analysisStatus, imageCount, illegibleNote,
                         analysisError, confidenceThreshold,
                         statistics: { categoryCounts, total },
                         errors: [ { errorIndex, written, intended,
                                     category, confidenceScore,
                                     locationOnScan, note, dismissed } ] }
Errors:   404 if no sample with that id.

Notes:
  - The client polls this until analysisStatus reads as analysed, then reads
    the SAME response's errors array for the review screen - no separate
    request. An earlier draft of this doc described a standalone
    GET /api/samples/:sampleId/report returning a distinct SampleReport
    shape (reportId, detectedErrors, ...); that endpoint was never built.
    Errors live embedded on this Sample (see the SAMPLES section intro), so
    this one route already is "the report."
  - Suggested poll interval: 2s, with a ceiling so a failed job does not
    poll forever.
  - If analysisStatus is FAILED, include the reason so the UI can show
    something better than a spinner that never stops.


GET /api/samples/:sampleId/images/:index
----------------------------------------
Serves the raw scan image bytes for the review screen.

Params:   index - zero-based position in the sample's image array
Returns:  200 + image bytes, with the correct Content-Type
Errors:   404 if the sample or that index does not exist.

Notes:
  - Indexed because Sample.sampleImages is Image[*] - a sample can be several
    pages. imageCount from the Sample payload tells the client how many exist.
  - Files live on disk (not GridFS at prototype scale), so this route resolves
    the stored path and streams it. Never expose the filesystem path itself in
    any JSON response.


(No separate GET /api/samples/:sampleId/report route - see the note on
GET /api/samples/:sampleId above.)


================================================================================
ERROR CORRECTION
================================================================================

PATCH /api/samples/:sampleId/errors/:errorIndex
------------------------------------------------
Applies a therapist's correction to a single detected error. errorIndex is
the error's position in the sample's embedded errors array (there is no
separate SampleReport/DetectedError collection or id - see the "embedded
errors" note under SAMPLES above).

Body:     a partial patch, at least one of:
            { "category": String,          // one of the five categories
              "dismissed": Boolean,        // true = remove the tag, false = restore it
              "confidenceScore": Number }  // 0-1; 1 = educator confirmed an uncertain tag
Returns:  200 + the updated Sample (same shape as GET /api/samples/:sampleId).
Errors:   400 if the body has none of the three fields, or an invalid value
          for one of them.
          404 if the sample or errorIndex does not resolve.

Maps to:  sampleController.reclassifyError(req, res) (server/controllers/sampleController.js)

Notes:
  - PATCH, not PUT. This is a partial update of a few fields; PUT means
    "replace the whole resource with the body I am sending", which is not what
    happens here.
  - "Remove" is also PATCH, not DELETE: the record is kept and dismissed
    flips to true, so the array position (and errorIndex) stays stable and the
    tag can be restored later. It does NOT keep a previousCategory/
    correctionNote/correctedAt audit trail - reclassifying overwrites the
    category in place with no history. That's a deliberate, logged scope cut
    (see client/DESIGN.md), not an oversight, and it means the "audit trail"
    half of this slice's original brief isn't implemented.
  - Returns the whole sample rather than the single error so the summary
    panel can repaint its counts from one response without a refetch.
  - Recommendation freshness is computed when the latest report is read: any
    usable sample updated after generation, or absent from basedOnSamples,
    marks the response isOutdated without adding audit-history fields.


================================================================================
TRENDS
================================================================================

GET /api/students/:studentId/trends
-----------------------------------
Returns aggregated error trends across all of a student's samples.

Query:    ?from=YYYY-MM-DD&to=YYYY-MM-DD   (optional; defaults to all time)
Returns:  200 + TrendData - counts and proportions per error category over the
          range, plus a per-sample series for the chart.
Errors:   404 if the student does not exist.
          400 if from or to is unparseable, or from is later than to.

Maps to:  ReportController.getErrorTrends(studentId, range)
          -> aggregateByCategory(sampleReports)

Notes:
  - Computed on demand from the stored SampleReports. There is no persisted
    trend entity, by design.
  - MUST exclude errors with status = REMOVED. A therapist who deleted a false
    positive expects it gone from the trend line. Getting this wrong makes the
    dashboard quietly disagree with the review screen.
  - Only samples with analysisStatus = COMPLETE contribute.

================================================================================
RECOMMENDATIONS
================================================================================

POST /api/samples/:sampleId/recommendations
------------------------------------------------
Generates and stores up to three approved worksheet recommendations for one
ANALYSED or REVIEWED sample.

GET /api/samples/:sampleId/recommendations
-----------------------------------------------
Returns the worksheet recommendations already stored for one sample.

POST /api/students/:studentId/recommendations
-------------------------------------------------
Generates a latest-only intervention report from all ANALYSED and REVIEWED
samples. A successful generation replaces older reports for that student.

GET /api/students/:studentId/recommendations/latest
-----------------------------------------------------
Returns the student's latest intervention report. Returns 404 when no report
has been generated.

GET /api/worksheets/:worksheetId/file
----------------------------------------
Streams an approved PDF through the server. worksheetId must exist in the
server-side Azure asset manifest; clients never submit Blob paths or SAS URLs.

================================================================================
NOTES AND DEFERRED
================================================================================

VERTICAL SLICE COVERED BY THE ABOVE
  create student -> upload sample -> poll status -> view report -> correct an
  error -> view trends. That is a complete demoable path with no gaps.

DEFERRED - AUTHORIZATION (not authentication - that part is done)
  POST /api/auth/login issues a JWT and every other route requires it. What's
  still deferred is ownership: Teacher is in the domain model but nothing
  scopes a request to the caller's own students, so GET /api/students still
  returns everyone regardless of who's signed in. Record it as a known cut so
  it does not get discovered live during the presentation.

ROUTE COLLISIONS TO AVOID
  Two routes that differ only by parameter NAME are the same route. Express
  matches on position, so /reports/:sampleId and /reports/:studentId collide
  and whichever registers first wins silently. Every collection above is nested
  under the resource that owns it, which is what keeps them distinct.
